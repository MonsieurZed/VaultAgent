# Exception `unsafe` limitée à `vaultagent-win32` (15/11/2026)

Tâche 0.1 du [plan de réécriture](../rust/plan.md) ; décision de Zed du 15/11/2026.

## Contexte

`docs/rust-pratiques.md` impose `#![forbid(unsafe_code)]` dans chaque crate et `conduite-check --crate` refuse
tout mot-clé `unsafe`. Le client Windows doit pourtant appeler l'API Win32 : identité et premier plan des
fenêtres, `SendInput`, DPAPI, clés NCrypt, WebAuthn (Windows Hello), icône de barre et carte d'approbation.
Ces appels passent par des fonctions FFI, toujours `unsafe` en Rust.

## Choix

- **Une seule crate** a le droit d'utiliser `unsafe` : `rust/vaultagent-win32`. Elle n'expose que des fonctions
  sûres ; aucun type ou fonction `unsafe` public.
- La crate le **déclare** dans son propre `Cargo.toml` :

  ```toml
  [package.metadata.conduite]
  unsafe = "FFI Win32 : fenêtres, SendInput, DPAPI, NCrypt, WebAuthn, icône de barre"
  ```

  La valeur est la justification, non vide. Une déclaration au niveau de l'espace de travail ne compte pas.
- Dans cette crate, chaque `unsafe` est dans une petite fonction dédiée dont le docblock contient une ligne
  `Sûreté : …` (préconditions tenues par l'appelant, pointeurs, durées de vie). Pas de commentaire dans le corps.
- `src/lib.rs` déclare `#![deny(unsafe_op_in_unsafe_fn)]` à la place de `#![forbid(unsafe_code)]`.
- Toutes les autres crates gardent `#![forbid(unsafe_code)]`.

## Contrôle

`conduite-check --crate` (patch de la tâche 0.2, dépôt Reseau) :

- sans déclaration : règles inchangées (`unsafe-non-interdit`, `unsafe-present`) ;
- avec déclaration : `unsafe-non-interdit` et `unsafe-present` ne s'appliquent pas ; la nouvelle règle
  `unsafe-non-justifie` signale tout `unsafe` dont le docblock le plus proche au-dessus ne contient pas
  `Sûreté :` ; une déclaration vide est signalée (`unsafe-declaration-vide`).

## Raisons

- Isoler `unsafe` dans une crate rend sa surface lisible et relisible d'un bloc ; le reste du code garde la
  garantie du compilateur.
- La déclaration dans le manifeste est explicite et visible en revue ; elle n'exige aucune liste tenue dans
  `conduite-check` lui-même, qui sert d'autres dépôts.
- `windows-sys` (liaisons brutes de Microsoft) plutôt que `windows` : moins lourd à compiler, et les
  enveloppes sûres sont écrites une fois dans `vaultagent-win32`.

## Conséquences

- La crate `vaultagent-win32` ne compile que sous Windows (`#![cfg(windows)]` dans `src/lib.rs`) ; sous Linux
  elle est vide et la suite reste verte.
- Ses tests Windows (fenêtre factice, aller-retour DPAPI) tournent sur TowerZ ; ils ne touchent ni réseau ni
  coffre réel.
- Toute nouvelle crate qui voudrait `unsafe` passe par une nouvelle note de décision validée par Zed.
